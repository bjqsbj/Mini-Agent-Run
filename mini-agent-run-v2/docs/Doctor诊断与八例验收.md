# Mini Agent Doctor · 八个单文件故障与验收手册

## 第一次运行

1. 在桌面的 `Mini-Agent-Run-代码修复版\mini-agent-run-v2` 中双击 `start.cmd`，保留终端窗口，浏览器打开 [本机排查台](http://127.0.0.1:4318)。需要 Node.js 22.18 或以上版本。若此前已有服务运行，先在旧服务的终端按 Ctrl+C，再启动并刷新页面。
2. 在默认的「Agent 故障诊断」选择 CASE-004，保留自动填入的用户反馈，选「离线证据回放」并点击「开始诊断」。也可以点「选择代码文件」，只上传 CASE-004 的 `.mjs` 文件。八个文件互相独立，均可单独上传。需要复现原文时，从清单复制完整反馈。[完整反馈与来源清单](../examples/doctor/catalog.json)
3. 查看执行轮次、模型的可见说明、工具参数及结果。报告生成后点击证据编号，页面会跳转并展开该次工具的原始返回。在 CASE-004 中核对模型参数分片、工具实际收到的参数以及轨迹上的派发时刻。
4. 使用真实模型时，在项目根目录的 `.env` 设置 `DEEPSEEK_API_KEY` 并重启。选择「DeepSeek · 动态工具调用」。真实模型先判断反馈是否可排查，再结合每轮返回值选择工具。模型会收到反馈、筛选所需的源码预览、所查询的代码及观测。离线选项按本地规则回放，只需本机资源。
5. 调查自己的模块时，可上传反馈相关的 JS/TS 文件及它们的本地依赖，再输入具体问题。也可展开「从公开 GitHub Issue 导入」，填入公开 Issue 的链接并点击「读取标题和正文」。导入需要本机能访问 GitHub；也可直接粘贴标题、正文和复现步骤。

这些文件按《测试示例.md》第三节构造，保留故障供测试。源码开头给出用户反馈及文档所引来源。日志、请求、虚拟时钟和外部服务状态均为本地合成。平台报告中的“修复验收标准”供修复后执行。要实际生成、测评和回滚候选源码，可进入「代码修复与回滚」，上传相关模块并提供输入和预期输出断言。完整项目的 `docs/操作运行手册.md` 给出了该入口的操作步骤。

## 八例对照

| 示例与源码 | 运行原始代码后，报告应该解释的证据 | 修改被测 Agent 后如何验收 |
| --- | --- | --- |
| CASE-001 · Thinking 一直不结束 · [CASE-001-thinking.mjs](../examples/doctor/CASE-001-thinking.mjs) | `read_file` 用时 800 ms，已完成。第二轮模型请求等了 480 秒仍无首 token，活动工具数为 0。核对等待阶段、模型请求及两类超时配置。 | 模拟首包永久不来和输出一半后挂起，分别触发首包、空闲超时；已有输出应保留。阈值内慢响应仍成功。超时进入失败终态，可在历史里重试。 |
| CASE-002 · 重复读取同一文件 · [CASE-002-loop.mjs](../examples/doctor/CASE-002-loop.mjs) | 26 次读取相同的 `src/app.ts`，观测哈希始终是 `abc123`，唯一结果数为 1。核对下一步选择、重复检测和步数上限。 | 设置 10 轮预算并重复返回相同结果，应在预算内结束；切换成返回值变化的合法轮询，应允许继续并受全局上限约束。 |
| CASE-003 · 停止后继续执行 · [CASE-003-stop.mjs](../examples/doctor/CASE-003-stop.mjs) | `STOPPED` 与模型流中止先于两个工具完成。工具未收到取消，迟到结果触发下一轮模型请求。按轨迹核对先后次序。 | 在模型流、单个工具、并行工具三处分别停止；再次停止也应安全。注入迟到结果，停止后的新增调用数应为 0，历史仅保留终止前已产生的内容及停止事件。 |
| CASE-004 · 工具参数丢失 · [CASE-004-arguments.mjs](../examples/doctor/CASE-004-arguments.mjs) | 五段参数可拼出 service=backend、keyword=ERROR、limit=100；调度器在首段尝试 JSON 解析并回退为空对象。工具校验报告缺少两个必填字段。 | 按不同位置切分 JSON，再交错两组调用。每个调用仅派发一次，参数与原对象完全相等。截断或缺必填字段时，应报告校验错误且零派发。 |
| CASE-005 · 429 重试风暴 · [CASE-005-rate-limit.mjs](../examples/doctor/CASE-005-rate-limit.mjs) | 初始模型调用曾成功；当前 8 个并发请求没有限流配置。首次 429 后又重试三次，虚拟时间戳始终相同。 | 返回 429、429、200 时应退避后成功；模拟持续 429，核对 1、2、4 秒退避、上限及 Retry-After。返回 401 时只请求一次；并发超限的请求排队。 |
| CASE-006 · 大日志卡顿与上下文溢出 · [CASE-006-large-log.mjs](../examples/doctor/CASE-006-large-log.mjs) | 工具已完成，原始输出 100,000 行、18,500,000 字节。模拟客户端映射 100,000 个节点，后端把全部字节传给模型并触发上下文错误。页面可检索第 100,000 行的 checksum 错误。 | 用下文的四档规模分别记录性能；原始错误行始终可查，前端节点受可见窗口或页大小限制，给模型的摘要受独立预算限制。浏览器中应能滚动、搜索和停止任务。 |
| CASE-007 · 重启后历史不全 · [CASE-007-history.mjs](../examples/doctor/CASE-007-history.mjs) | 存储里有 86 条事件和最终报告。API 首次返回 20 条，页面显示 20 条，hasMore=true，页面只请求过一次。核对分页消费位置。 | 重启后取得 86 个唯一事件 ID 并展示最终报告。验证少于一页、刚好一页、多页，以及中间页失败后重试，检查无漏项、无重复。 |
| CASE-008 · MCP 重连后找不到工具 · [CASE-008-mcp.mjs](../examples/doctor/CASE-008-mcp.mjs) | 连接状态是 CONNECTED，服务端发布 3 个工具；当前会话注册表为空，下一次模型请求也拿不到工具定义。 | 同一会话断开再重连，确认发现、注册和下一轮请求三处的工具集一致，`read_file` 可调用。重复重连无重复项；服务端删除的工具从会话移除。 |

## 脱离平台核对现场

在项目根目录或示例压缩包解压后的根目录运行。每个文件都可替换到第一条命令中执行，返回 JSON 现场，无需安装依赖。

```powershell
node examples/doctor/CASE-004-arguments.mjs
node examples/doctor/CASE-006-large-log.mjs --bench
node --input-type=module -e "import {observe} from './examples/doctor/CASE-007-history.mjs'; console.log(observe({count:10}).session)"
```

最后一条命令将数据库事件数改为 10。此时第一页包含全部事件，`hasMore` 为 false，报告应可见。进一步测试平台时，复制 CASE-007 文件，将 `observe` 的默认 `count` 从 86 改成 10，文件另存为任意名称并上传，粘贴原反馈。离线诊断应返回「证据不足」。该测试能发现仅按文件名或反馈返回预置结论的实现。

CASE-006 的 `--bench` 在 Node 中实际生成 100、1,000、10,000、100,000 行，测量生成、首批 50 行切片和检索耗时，列出堆用量变化、错误行号及摘要字节数。单次耗时会随机器与垃圾回收变化。现场中的 2,800 ms 和 3,800 MiB 是文档提供的模拟数据。要测网页性能，在浏览器开发工具 Performance 中录制打开日志、翻页、定位错误和点击停止的过程。

## 怎么核对平台本身

- **工具选择**　在真实模式对比 CASE-005 与 CASE-007。前者应取模型请求和重试配置，后者应查持久化与会话分页。证据指向可从轨迹、源码和独立通道相互核对的同一问题。不同真实运行可能选择相邻的关键步骤，按引用和因果关系验收。
- **停止与重试**　选择 CASE-003，在 Doctor 查询工具且显示执行中时点击「停止」。这次排查应进入停止终态。点击「重新执行」后产生新记录，旧记录仍可打开。让新任务运行到底，即可看到示例中被排查 Agent 的取消缺陷。
- **日志与历史**　运行 CASE-006，定位第 100,000 行，或检索 `checksum`。刷新，再从同一数据目录重启服务，回到历史记录。原始行号、已完成报告和证据应可再次打开。
- **输入质量**　单独输入“我觉得 Agent 不好用”，应提示补充现象。输入“解方程”，应标记为无关。对没有运行轨迹的普通源码，报告应指出缺失的证据；给出具体运行现场后再验证根因。

## 上传自己的观测模块

默认文件格式为 JS/TS 的 ES 模块。最多上传 32 个文件，合计 80 KiB。若具备可复现的现场，导出一个同步 `observe()`，返回可 JSON 序列化的对象；多文件时在页面选择入口。相对依赖随源码一起上传。QuickJS 在隔离环境执行函数，现场以 JSON 跨边界传递；单次观测应精简至 8,192 个字符以内。大型归档可以像 CASE-006 那样按相同连续行压缩。普通项目源码也可供模型查看；进程外的模型服务、MCP 或数据库现场需由明确的采集数据提供。

| 字段 | 读取它的诊断工具 |
| --- | --- |
| status、trace、config | get_run_status、get_execution_trace、get_agent_config |
| logs、archive | search_logs，保留原始行号，页面每页 50 行 |
| tools、models | get_tool_calls、get_model_requests |
| storage、session、mcp、metrics | get_storage_status、get_session_status、get_mcp_status、get_resource_metrics |
| 上传源码、相对路径、行号 | inspect_code_snippet，支持定位片段 |

## 实现与报告校验

`examples/doctor/catalog.json` 将案例编号、用户问题、来源和文件名关联。服务端以本次上传内容或选中的示例建立输入快照。`server/doctor/tools.ts` 在隔离执行器采集现场，并按模型请求返回对应通道。每次成功查询取得本次运行内的 E 编号。真实模型逐轮接收已查询的观测，可针对新的线索继续调用工具。原始输入、观测与事件通过 SQLite 保存，重新执行从冻结的输入另建任务。

`server/doctor/run.ts` 协调语义筛选、工具循环和最终报告。`server/doctor/report.ts` 检查报告引用的编号、原文摘录和轨迹位置。确认根因至少需要跨两轮、三种工具的证据，包括执行轨迹及源码；无法定位时允许输出「证据不足」。校验保证可追溯，结论的因果解释仍可通过报告中的链接人工核对。离线规则及测试期望保存在调查现场之外，真实模式只读取所选模块和调查得到的信息。

在项目根目录运行 `npm.cmd test`。八个主测试逐份执行单文件，再给源码改名后上传到诊断执行器，逐项断言关键步骤、故障特定通道、引用和报告。附加测试覆盖反事实、无现场的源码、伪造引用、日志原始行号、输入筛选及 Issue 导入。
