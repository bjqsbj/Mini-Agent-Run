# 项目详解 · 从一条投诉到一个可回滚的修复

默认的 Doctor 诊断使用独立的工具循环。上传源码通过隔离执行器提供观测，模型决定下一轮查询，最终将轨迹步骤、根因与可复核的证据关联。诊断模块、观测字段和报告校验见[Doctor 设计与八例验收](Doctor诊断与八例验收.md)。本文详解「代码修复与回滚」入口。

## 1. 跟随一次具体执行

Agent 同时发出 call_A 和 call_B。后者先返回，调度器把结果写给派发队列首位的 call_A。界面中的第 27 行模拟日志记录了这次错配。上传示例里，`src/dispatch.ts` 的 `collect` 按完成顺序遍历事件，却从派发队列取 ID。单工具或顺序完成的测试都会漏掉这个错误。

清单案例生成的修改把 `toolMessage(pending[index], event.value)` 中的 `pending[index]` 改为 `event.id`。`src/message.ts` 负责组装最终消息。隔离执行器同时加载两个模块，逐一对比返回数组内每条消息的角色、调用 ID 和内容。测试先在原始代码上运行，再在候选代码上运行。通过后可直接下载可读的源文件。

## 2. 三条数据路径

```text
源码 + 问题 → 导入快照 → 规则 → LLM 筛选 → 模型请求工具 → 本地观测 → 模型定位
                                                  ↑           │
                                                  └──下一轮─────┘
定位结果 + 原始源码 → 冻结断言 → 基线测评 → Coding Agent 精确补丁 → 候选测评
                                                              ↓
                                       全部通过且基线仍为活动版本 → 新版本
每个阶段 → SQLite 事件 → SSE → 可回看的任务详情；原始日志另行分页读取
```

| 代码入口 | 读代码时关注什么 |
| --- | --- |
| `server/main.ts` | API、上传请求体上限、同源检查、启动恢复和 SSE 续传 |
| `server/codebase.ts` | JSON 清单、源码路径和断言校验、项目快照、精确替换及回滚 |
| `server/repair.ts` | 两层筛选、先测基线、生成候选、逐项评估 |
| `server/runner.ts` | 整个生命周期、决策轮数、工具调度、取消和终态事务 |
| `server/model.ts` | DeepSeek 流式文本、工具参数分片，以及结构化筛选 / 修改请求 |
| `server/tools.ts`、`scenarios.ts` | 四组模拟运行现场；工具输出样本、原始行号和上下文 |
| `server/evaluate.ts`、`engine/worker.mjs` | Worker 生命周期、转译、QuickJS 模块解析及宿主侧结果比较 |
| `web/src/SourceInput.vue`、`StageReport.vue`、`CodeVersions.vue` | 导入源码/断言、逐项前后对照、版本切换与源码 ZIP |
| `tests/repair.test.mjs`、`app.test.mjs`、`model.test.mjs` | 案例回放、真实 HTTP 生命周期、模型流式协议和错误处理 |

## 3. 为什么同一句“不好用”可能得到不同处理

「我觉得Agent不好用」缺少可观察现象，规则返回待补充，记录需要的信息。「解方程」属于明确无关请求，规则直接结束。「我觉得 Agent 不好用：两个工具逆序返回时 ID 对错了」包含可检验现象，会进入下一层。规则只短路明确模式。真实模式把问题、文件路径及各文件前 1,200 字符发给模型，要求给出 accept、clarify 或 reject，并记录理由。缺密钥或上游出错会产生失败记录，可修正配置后重试。

通过筛选后，诊断模型看到完整选定源码。它可以查询服务状态、检索日志、核对配置。工具调用和返回用同一个 tool_call_id 关联，再次发送给模型。修复流程必须先有工具观测；若模型直接回答，Runner 要求其先取证。每次最多 8 轮，整次任务限时 180 秒，当次模型请求限时 65 秒。SSE 显示公开文本和工具行为。

四个现场是 gateway、sync、exporter、agent。观测来自可复现的合成数据。上传业务项目时要选择相关现场，并用该模块的独立行为断言检验结论。状态和日志并不会自动连接到上传者的真实生产环境。

## 4. 生成候选与可靠性判断

1. **锁定基线。** 每条任务关联源码项目、精确的基础快照、案例和断言。内置案例从文件取断言，上传者也可粘贴或导入自定义 JSON。若自由上传后留空，真实模型先拟定断言并保存来源，之后才生成补丁。模型拟定的预期仍需要人核对。
2. **测原始版本。** TypeScript 转译为 ES 模块，QuickJS 在独立 Worker 中加载已上传的模块，调用给定导出函数。函数的实参进入虚拟机，宿主用深度相等比较实际与预期结果。每条断言新建运行时，避免上一条修改全局状态影响下一条。
3. **明确改哪里。** Coding Agent 获得反馈、整个源码快照、诊断结论和失败输入，返回一组 `path / before / after`。仅在已上传的文件中查找唯一原文并替换。任一处不匹配或有歧义，整个候选作废，已有代码可回看。
4. **用同一把尺复测。** 已通过全部断言的基线不会新增修复版本。有失败项时才生成候选，界面记录修改前后代码与逐项测评。所有断言都通过才能发布。失败候选的替换内容和结果保留在事件中。
5. **比较结果的含义。** 实测的是这些输入上的函数行为。转译检查语法，工程级类型检查、端到端部署、外部依赖及生产流量仍属于原仓库的集成验证。普通运行依靠随包分发的 JS/WASM，用户无需安装编译器。

受测代码在 QuickJS/WASM 中运行。项目只提供上传文件的模块加载器，允许相对导入，包括源码中的 `.js` 引用对应上传的 `.ts`。测评无宿主网络、磁盘和 shell 接口。每项限制 16 MiB 虚拟机内存和约 400 ms 执行时间，每批由 Worker 的 15 秒上限兜底。异步返回、不可序列化或超限的结果会记录为失败。详情见 [QuickJS 封装项目](https://github.com/justjake/quickjs-emscripten)。

## 5. 多任务同时修复和回滚时会发生什么

原有 runs、events、logs 三张表保留。projects 保存活动版本 ID，revisions 保存不可变文件快照、父版本、生成类型和来源任务，assignments 把每条任务绑到特定基线。

两个任务若从同一基线出发，先完成者在事务内检查并更新活动版本。后完成者只可在活动版本仍等于其基线时写入，否则任务提示版本变化。修复发布与任务完成共用一个事务。回滚先读取目标版本，再追加类型为 rollback 的快照。原始版本、修复版本以及每次回滚均可查看和下载。用户磁盘上最初选中的文件保持在原位置，下载 ZIP 可取出所需版本。

停止会取消当前模型请求、工具等待或测评 Worker。重试创建新的任务记录，以当前活动代码作为新基线。进程重启会将遗留运行任务标为中断，同时保留已保存事件和快照。默认一个服务进程使用一个数据目录。

## 6. API 对照

| 方法与路径 | 作用 |
| --- | --- |
| GET /api/config | 场景和可读案例清单、凭证配置状态 |
| POST /api/runs | 提交 question、scenario、mode 与 repair；返回 runId（字段 id） |
| GET /api/runs/{id}/events | 原生 SSE，支持 Last-Event-ID 续传 |
| GET /api/runs/{id}/logs | 以 service、level、q、page 读取原始日志，每页 50 行 |
| POST /api/runs/{id}/stop 或 retry | 停止或创建新运行 |
| GET /api/runs/{id}/code | 项目 ID、基线、当前版本、断言、版本列表 |
| GET /api/runs/{id}/revision?id=版本ID | 指定版本的路径与完整源码。网页将这些文件打成 ZIP |
| POST /api/runs/{id}/rollback | 请求体传 target、head，分别为目标版本与操作时看到的活动版本 |

普通网页统一提交 repair。只传 `{"caseId":"parallel-tools"}` 时从清单导入；传 files 数组时使用上传源码，checks 为可选的行为断言。继续排查可传 project 以复用已有项目。旧版仅诊断 API 请求仍支持回放与重试。
